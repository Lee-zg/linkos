# LinkOS 产品体验诊断与迭代路线建议

日期：2026-09-23。状态：诊断已完成，优化设计与路线为待确认建议；未修改业务代码、未创建提交。

## 1. 结论

LinkOS 已具备真实登录、聊天、分片传输、代码版本、管理以及 Runner/插件基础，但“能操作一个模块”和“多人能完成协作任务”之间仍有明显断点。当前优先级不是统一换皮或增加更多应用，而是：**数据不受损 → 反馈可信 → 发出后对方能接收 → 内容能找回 → 执行结果可追溯**。

建议沿用 PRD 的局域网团队定位，以团队日常协作为主线，同时保留研发团队的差异化能力。用户本轮未指定优先场景；这是一项可调整的建议，不是新的产品定位决定。

## 2. 证据范围与限制

- 源码覆盖 9 个页面/区域：接入、桌面与 Dock、文件、聊天、代码、任务、管理后台、应用管理、设置。
- 使用独立端口的内存网关和 Chromium 151，实际操作登录、设置、文件上传下载、第二成员访问、聊天、代码编辑保存、任务空态与管理后台。
- 桌面 1440×900，手机模拟 390×844；所有业务写入仅针对临时测试账号/文件，不触碰真实工作区数据。
- 已有未提交源码改动保持原样。部分旧知识卡片仍描述原生 CSS/Runner stub，与当前 Tailwind、桌面窗口和隔离执行实现不一致，不能据此判断现状。
- 没有生产性能基线、真实使用频次、访谈或转化数据；严重度、成本与优先级为启发式判断。
- 未启动容器 Runner，未验收实际执行/产物、生产插件签名安装、真实设备吊销及移动真机输入法；这些结论标注为源码确认或待验证风险。
- 本报告不替代安全审计、完整 WCAG 审计或真实用户测试，不给产品整体打分。

### 最关键的实测问题

1. 临时代码文件原有 **2,105 行**，只加载 **2,000 行**，编辑保存后新版本只剩 **2,000 行**。这是发布阻断项，不是普通体验细节；旧版本可能可恢复，不能据此允许静默覆盖。
2. 成员 A 上传文件成功，成员 B 的“最近”仍为空；“共享目录”显示硬编码样例，没有该文件。
3. 关闭聊天窗口会丢失未发送草稿。
4. 系统通知开关关闭后重开即恢复开启；诊断包显示成功，但未产生下载。
5. 390px 手机视口中管理员 Dock 宽 501px，左右均被裁切；聊天频道列表隐藏且没有替代切换入口。

## 3. 三种优化路径

| 路径 | 收益 | 代价/不足 | 建议 |
| --- | --- | --- | --- |
| 只修明显缺陷 | 风险小，最快解除数据安全阻断 | 共享与跨应用上下文仍断裂，不能证明团队价值 | 作为第一阶段，不作为全部路线 |
| 保留桌面外壳，逐步补齐任务流程 | 保留已有投入，直接改善多人任务成功率 | 需要补资源索引、状态与深链接，不只是 CSS 调整 | **推荐** |
| 全面重做成传统 SaaS 布局 | 导航范式统一，移动方案容易独立设计 | 重写成本高，无法自动解决数据/协议问题，且尚无用户证据证明应弃用桌面 | 暂不采用 |

## 4. 产品优化方案

### 4.1 工作台与信息架构

保留现有桌面背景、多窗口和应用品牌，不强制更换浅/深主题。新增轻量“工作台”作为可配置的默认入口，聚合未读消息、最近共享、进行中的任务；无数据时只展示加入频道、分享文件和邀请同事的下一步，不用演示数据填满页面。

建议组织：

- 普通成员：工作台、聊天、文件；代码与任务为进阶入口。
- 管理员：增加成员与访问、运行节点、应用管理、审计入口，不把部署术语灌入普通成员页面。
- 顶层始终能确认当前工作区、身份和连接状态。角色影响动作与说明，服务端鉴权仍为最终边界。
- 手机底部：工作台 / 聊天 / 文件 / 更多；频道和文件用抽屉选择，窗口控制简化成明确返回。
- 频道、文件、任务均有稳定深链接；访问前检查工作区与权限，不能绕过授权。

### 4.2 文件协作闭环

目标路径：选择文件 → 显示传输阶段 → 上传成功 → 发送到频道 → 对方打开文件卡片 → 鉴权下载 → 在共享目录找回。

- “最近”可以保留个人视角，但必须清楚说明范围；“共享”必须由服务端工作区资源索引驱动。
- 资源最小元数据：名称、大小、类型、上传者、创建时间、工作区、资源 ID、可访问范围；权限不足和资源失效需要单独状态。
- 文件卡片显示可识别内容、发送人、大小和下载操作，不把 SHA256 当主标题或默认说明。
- 传输状态为工作区级；关文件窗口不丢队列。提供取消、失败原因和继续入口；重选原文件才能续传时必须明确说明。
- “校验 100%”“传输 100%”“文件可用”是不同状态，不能用一个进度条混淆。
- 不在第一版承诺复杂目录权限继承、批量同步盘或全文内容检索。

### 4.3 聊天与内容找回

- 草稿按工作区、用户、频道/线程隔离；关窗/刷新可恢复，发送成功才删除。
- 补发送中、失败、重试与中文输入法保护；同一消息重试使用稳定标识。
- 历史消息分页和搜索结果定位保留滚动位置；用户阅读旧消息时不强制滚到底部。
- 优先补文件引用卡片；代码行、任务结果引用在对应资源深链接稳定后接入。
- 未读与通知分开：先有正确的未读计数和已读状态，再做可授权、可关闭且真实生效的系统通知。

### 4.4 代码与任务

- 先禁止截断内容覆盖保存；所有“已保存”提示必须建立在完整内容和持久化成功上。
- 代码页统一“保存并运行”：展示项目、版本、命令和执行策略，确认后创建任务；不能把未保存草稿与服务器版本混为一谈。
- 当前任务状态按 ID 隔离；任务列表可回到历史详情，而不是只保留一个 currentJobId。
- 任务状态：未提交、排队、准备、运行、成功、失败、取消、超时；无 Runner、无权限、日志加载失败各有说明和下一步。
- 产物使用统一鉴权下载，运行结果可分享回频道；验收必须包含真实容器产物，不以出现列表作为成功。

### 4.5 管理与可信反馈

- 设备吊销展示作用对象和影响，明确“这是当前设备”，提供确认、进行中、成功/失败。后端不可撤销时不设计假撤销按钮。
- 中文角色名配权限摘要，原始角色 ID 收入详情；角色变化后刷新用户实际能力。
- 未实现的通知、自动启动、诊断包和插件预览明确标注能力边界，不再弹“成功”。
- 统一反馈语义：成功 / 错误 / 警告 / 信息；关键错误在对应区域保留，不能只依靠自动消失的通知。
- 诊断包后续只收集必要信息，提示包含范围并脱敏，不默认收集消息、文件内容和凭证。

### 4.6 状态设计最低标准

| 区域 | 空 | 加载 | 错误 | 边界 | 权限 | 离线 |
| --- | --- | --- | --- | --- | --- | --- |
| 接入 | 未发现工作区，允许手填 | 连接/鉴权分阶段 | 地址错误与连接失败分开 | 邀请过期、重复申请 | 当前身份与审批状态 | 重试、切换地址 |
| 聊天 | 无消息与搜索无结果分开 | 首次加载与增量加载分开 | 原位重试、保留草稿 | 输入法、长消息、旧历史 | 无发送权限解释 | 保留草稿，标记旧内容 |
| 文件 | 无共享文件，提供分享动作 | 校验/上传/合并 | 失败项可恢复 | 空文件、大文件、重名 | 无权访问与资源不存在不混淆 | 队列保留、等待重连 |
| 代码/任务 | 无文件、无任务、无产物分开 | 全文加载、排队、日志加载 | 冲突、执行失败、下载失败 | 截断、超时、长日志 | 无编辑/执行权限解释 | 草稿与执行状态更新时间 |
| 管理 | 无待审批、无节点 | 请求中的动作禁重入 | 就地反馈 | 当前设备、最后一个高权角色 | 权限被回收 | 禁止不可验证的提交 |

这是交付边界清单，不代表这些设计已经实现，也不是完整无障碍规范。

下列为**顺序与发布门槛**，不是承诺上线日期。尚未获得团队人数、投入与截止时间，因此不提供虚假精确排期；每阶段在工程拆解后估时。前一阶段的阻断问题未解除，不进入扩大试点。

| 阶段 | 用户结果 | 功能范围 | 依赖 | 发布门槛 |
| --- | --- | --- | --- | --- |

## 6. 后续功能池与暂缓项

### 在协作闭环稳定后评估

- 消息 @成员、未读与通知偏好：先明确已读语义，避免制造提醒噪音。
- 文件预览、名称搜索、筛选与收藏：由真实资源索引支撑；全文索引按数据规模另评估。
- 任务模板与收藏命令：建立在版本绑定和执行策略稳定之上，不开放任意不受控命令。
- Git 状态/差异查看、轻量文档与看板：先验证是否减少现有任务中的切换，而不是因插件体系可扩展就全部开发。
- 备份与恢复的管理员可操作入口：必须先验证恢复演练、数据范围和停机约束。

### 暂缓

CRDT 多人逐字编辑、白板、音视频、完整 Git 托管、多租户计费、公网联邦、SSO 大改、开放插件市场与泛化 AI 助手。部分能力在旧文档路线中，但没有必要抢在文件共享与数据安全之前；后续以试点需求、维护成本和安全边界决定是否进入。

## 7. 度量与验证方案

### 核心指标建议

**北极星候选：每周完成至少一次跨成员协作闭环的工作区数。** 一次闭环可先定义为 A 分享资源、不同成员 B 成功打开并完成鉴权下载；研发场景再扩展为结果被另一成员查看。不是当前已埋点或已达成指标。

| 层级 | 指标/事件 | 定义与使用 |
| --- | --- | --- |
| 激活 | workspace_joined → first_collaboration_completed | 新成员首次进入至完成闭环的时长与完成率，审批等待时长单独统计 |
| 主链路 | upload_completed → resource_shared → recipient_download_succeeded | 按匿名化资源 ID 与不同成员关联，不采集内容；失败记录 error_code |
| 留存 | weekly_collaborating_workspaces、returning_members | 看真实协作而非只开网页；试点样本小时报告原始人数和任务数，不做显著性结论 |
| 可靠性 | draft_restore_result、code_save_integrity、job_result_viewed | 代码完整性先用回归/一致性校验，线上只记录结果元数据 |
| 护栏 | download_failures、duplicate_sends、permission_denials、unexpected_revocations | 以原因分组，不能通过放宽权限降低错误率 |
| 性能 | 首屏可交互、INP、首次哈希期间长任务、峰值内存、重连恢复时长 | PRD 的 P95 1.5s/消息 150ms 是原目标，不是本轮测量值；为网段/设备定义测试条件后验收 |

未有基线时不承诺“提升 20%”。先完成任务测试与试点基线，再确定业务目标；数据完整性和越权失败应作为零容忍回归门槛，而非平均值指标。

### 试点方法

1. 邀请 5–8 名符合目标的真实使用者，包含首次用户、研发成员和管理员。该样本用于发现问题，不用于推断总体转化率。
2. 不指导地完成：加入工作区；发文件给同事并让对方下载；关闭窗口找回草稿；手机切换频道；查看对应版本的任务产物。
3. 记录任务成功、求助次数、误操作、耗时及原因；本报告的高严重度发现逐项验证。
4. R0/R1 通过后再考虑 20–50 人团队试点，前提是部署、安全、备份与容量门槛达标。
5. 埋点和诊断只留必要元数据，不记录消息正文、代码、文件内容、凭证或完整网关地址；部署方可控制采集范围和保留期。
